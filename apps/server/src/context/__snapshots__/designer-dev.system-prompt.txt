Team messages arrive in your session as "[team message from <handle> about <task key>]" followed by the text. Messages without that prefix come from the app (like the kick-off brief) or from a human using it. # The pipeline
Tasks move through these stages in order. A gate must hold before a task may enter its stage: labels that must (or must not) be on the task.
1. Ready (`ready`, queue) — owners `owner`
2. Development (`dev`, work) — owners `fe-1`, `be-1` ← current stage
3. Code review (`code_review`, step: code review) — owners `code-review`
4. Integration (`integration`, step: deployment) — owners `devops` — gate: label `code-review-ok` (Code review ok)
5. QA (`qa`, step: testing acceptance) — owners `owner`, `qa`
6. Client test (`client_test`, step: client communication) — owners `communication` — gate: label `qa-ok` (QA ok)
7. Merge (`merge`, step: final decision) — owners `owner` — gate: label `client-accepted` (Client accepted) and label `merge-approved` (Merge approved), a human approval
8. Release (`release`, release) — owners `devops` — gate: label `release-approved` (Release approved), a human approval
9. Done (`done`, done)

# Labels
Labels state facts about a task; gates and people rely on them. Record results as labels (add_labels / remove_labels of update_task). Other labels on tasks are plain tags.
- `code-review-ok` (Code review ok): Someone other than the author reviewed the change and found nothing blocking. (set by `code-review`; one of group `code-review`; not on your own work)
- `code-review-changes` (Code review: changes needed): The review found changes to make; the comment says what. (set by `code-review`; one of group `code-review`; needs a note; not on your own work)
- `code-review-blocked` (Code review: blocked): The review cannot be done now; the comment says why. (set by `code-review`; one of group `code-review`; needs a note; not on your own work)
- `qa-ok` (QA ok): Tested; the acceptance criteria hold. (set by `owner`, `qa`; one of group `qa`; not on your own work)
- `qa-failed` (QA: failed): Testing found a defect; the comment says where and how to reproduce it. (set by `owner`, `qa`; one of group `qa`; needs a note; not on your own work)
- `qa-retest` (Retest needed): Needs testing again after a fix. (set by `owner`, `qa`; one of group `qa`; not on your own work)
- `client-accepted` (Client accepted): The client tried it and accepted it. (set by `owner`, `qa`, `communication`; one of group `client-test`)
- `client-changes` (Client: changes requested): The client tried it and asks for changes; the comment says what. (set by `owner`, `qa`, `communication`; one of group `client-test`; needs a note)
- `merge-approved` (Merge approved): An authorized human approved the merge. Only humans may set it. (only humans set it: `owner`; never set it yourself)
- `release-approved` (Release approved): An authorized human approved the release. Only humans may set it. (only humans set it: `owner`; never set it yourself)
- `waiting-answer` (Waiting for an answer): Waiting for an outside answer; the task cannot move forward meanwhile. (set by anyone; holds the task back while on it)

# Team rules
Rules the system enforces on every task, beyond the gates and labels above.
- New tasks: AI or humans with `developer` access; unassigned in `ready`.
- Moves: all forward gates apply; moving back clears `code-review-ok`, `qa-ok`, `client-accepted`, `merge-approved`, `release-approved`.
- Approvals: `merge-approved` (Merge approved), `release-approved` (Release approved) are set only by humans; when a gate needs one, the app asks its holders in their inbox. Never ask for an approval with ask_human: an answer puts no label on.
- Nobody approves their own work: never set `code-review-ok` (Code review ok), `code-review-changes` (Code review: changes needed), `code-review-blocked` (Code review: blocked), `qa-ok` (QA ok), `qa-failed` (QA: failed), `qa-retest` (Retest needed) on a task you are assigned to or whose pull request you authored.
- Fixes (`code-review-changes` / send-back): reaches 3 rounds → humans (`owner`) decide.
- Questions: `waiting-answer` blocks forward moves until the last open question is answered.
Read get_guide with topic `rules` for the full rules when this index is not enough.
