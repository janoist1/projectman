# Labels
Labels state facts about a task; gates and people rely on them. Record results as labels (add_labels / remove_labels of update_task). Other labels on tasks are plain tags.
- `code-review-ok` (Code review ok): Someone other than the author reviewed the change and found nothing blocking. (set by `code-review`; one of group `code-review`; not on your own work)
- `code-review-changes` (Code review: changes needed): The review found changes to make; the comment says what. (set by `code-review`; one of group `code-review`; needs a note; not on your own work)
- `code-review-blocked` (Code review: blocked): The review cannot be done now; the comment says why. (set by `code-review`; one of group `code-review`; needs a note; not on your own work)
- `qa-ok` (QA ok): Tested; the acceptance criteria hold. (set by `owner`, `qa`; one of group `qa`; not on your own work)
- `qa-failed` (QA: failed): Testing found a defect; the comment says where and how to reproduce it. (set by `owner`, `qa`; one of group `qa`; needs a note; not on your own work)
- `qa-retest` (Retest needed): Needs testing again after a fix. (set by `owner`, `qa`; one of group `qa`; not on your own work)
- `client-accepted` (Client accepted): The client tried it and accepted it. (set by `owner`, `qa`, `communication`; one of group `client-test`)
- `client-changes` (Client: changes requested): The client tried it and asks for changes; the comment says what. (set by `owner`, `qa`, `communication`; one of group `client-test`; needs a note)
- `merge-approved` (Merge approved): An authorized human approved the merge. Only humans may set it. (only humans set it: `owner`; never set it yourself)
- `release-approved` (Release approved): An authorized human approved the release. Only humans may set it. (only humans set it: `owner`; never set it yourself)
- `waiting-answer` (Waiting for an answer): Waiting for an outside answer; the task cannot move forward meanwhile. (set by anyone; holds the task back while on it)

# Commands that run without asking
Every other shell command waits in a human inbox until someone approves it, and the owner is often away: a blocked session can lose hours. So write your commands in the forms below. The server judges the command text only, not what it would do.
- Reading: read-only commands run without asking in your working directory (the task's worktree). They are `git` with `status`, `diff`, `log`, `show`, `rev-parse`, `merge-base`, `ls-files`, `blame`, `grep`, `shortlog`, `describe`, `diff-tree`, `name-rev`, `cat-file` (and `git branch` only to list); `grep`, `rg`, `tail`, `sort`, `uniq`, `find`, `file`, `printf`, `cat`, `head`, `wc`, `ls`, `pwd`, `echo`, `cut`, `tr`, `nl`, `stat`, `du`, `diff`, `basename`, `dirname`, `realpath`, `true` (`find` without `-exec` or `-delete`, `sort` without `-o`, `tail` without `-f`, `xargs` only after a lister such as `git ls-files`); no `git -c`, no `--output`.
- Project checks: `npm test`, `npm run test`, `npm run typecheck`, `npx vitest run`, `npx tsc --noEmit`, `npx prettier --check`, without `-u`, `--update`, `-w`, `--write`. Claude Code also pre-approves `npm run build`, `npm run format`, `npm run lint`, `npx vitest`, `npx tsc`, `npx prettier` with any arguments.
- Formatting is a routine step in your own worktree: `npx prettier` with `--write`, `-w` and one or more paths inside the worktree (no other options), or `npm run format` without extra arguments. These are not read-only checks. They may run in a chain, as the first stage of a pipe into readers, and with `>/dev/null 2>&1`: `npx prettier --write src/a.ts >/dev/null 2>&1; npm run typecheck 2>&1 | head -20`. Paths outside the worktree wait for a human.
- Your routine steps in your own worktree: `npm ci` or `npm install` (only with `--prefer-offline`, `--no-audit`, `--no-fund`), `git add` (`-A`, `--all`, `-u`, `--update` or paths inside the worktree), `git commit -m "message"` (also `-a`, `--all`, `-q`, `--quiet`; a message of several lines inside the quotes is fine, so is a second `-m`; no `--amend`, `--no-verify` or `-F`), `git merge --ff-only main` (or a commit id) with `-q`, `--quiet` if you like. Each is one command. It may be followed by `2>&1` and a pipe into readers that only filter its output (`npm install --prefer-offline --no-audit --no-fund 2>&1 | tail -3`), but a `tee` or any other writer after the pipe waits for a human. Readers may stand between them in a chain. A chain with a routine step may start with `cd` to the working directory itself and has no other `cd`: `cd apps/server && npx vitest run && git add -A` waits for a human.
- Chaining: `&&`, `||` and `;` between commands, `|` between the stages of a pipeline, all on one line (a newline between commands is refused). Redirections: only `2>&1`, `>/dev/null`, `1>/dev/null`, `2>/dev/null`.
- Quotes: put a pattern or a message in single quotes, which are literal: `grep -n 'task\.(edit|save)' src`. Double quotes work too, but a `$` or a backtick inside them refuses the command, and a backslash there escapes only `$`, a backtick, `"` and `\`. A text with an apostrophe goes in double quotes.
- Paths: relative or absolute, but inside the directories above; no `~`, no `..` behind a directory name. `cd` only into such a directory; `git -C <dir>` only when the directory is the one you are in. When a chain changes directory, join its parts with `&&`, not `;` or `||`: otherwise the server checks later relative paths from every possible directory, since an earlier `cd` may have failed or been skipped. For example, `cd apps/server && npx vitest run test/member-instructions.test.ts 2>&1 | tail -15; cd ../web && npx vitest run src/features/team 2>&1 | tail -15` waits for a human; `cd apps/server && npx vitest run test/member-instructions.test.ts 2>&1 | tail -15 && cd ../web && npx vitest run src/features/team 2>&1 | tail -15` runs without asking.
- Never without asking: interpreters and shells (`python`, `node`, `perl`, `sed`, `bash -c`), shell variables and substitution (`$VAR`, `$(...)`, backticks), `{a,b}` braces, `~`, `!`, a single `&`, here-documents and any redirection into a file (`>`, `>>`, `<`). Change files with your file-editing tools, not through the shell.
- Refused without asking anyone: a command that rewrites a file in place (`sed -i`, `sed --in-place`, `perl -i`, `perl -pi -e ...`), alone or in a chain. It is answered at once with a pointer to your `Edit` and `Write` tools, which need no permission: use them.
